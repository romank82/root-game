Ниже — единая дорожная карта доработки ROOT Game. Она построена так, чтобы не ломать текущий проект, не удалять данные преждевременно и постепенно перевести все игровые правила из кода в БД и админ-панель.

Главный принцип
В коде остаются только:

универсальный игровой движок;
проверка прав, статусов и состояний;
финансовые и антифрод-проверки;
API, интеграции TON/Telegram/геолокации;
админский approval workflow.
В админке и БД настраиваются:

задания, геозоны, AR-объекты, мини-игры;
ключи, награды, цены, вероятность и правила магазина;
доступность миссий, лимиты и попытки;
команды и параметры командных заданий;
экономические правила ROOT;
переводы, комиссии, пороги;
права администраторов;
блокировки, страны и операционные политики.
Этап 0. Проектирование и инвентаризация текущего состояния
Цель: не начинать реализацию вслепую и не потерять уже работающие части.

0.1. Снимок текущего проекта
Проверяем:

структуру backend, frontend и Docker;
текущее состояние PostgreSQL и Alembic;
существующие модели и миграции;
фактические API;
текущую реализацию авторизации Telegram;
хранение игроков, инвентаря, кошельков, транзакций;
состояние админ-панели;
где запускается demo seed;
какие демо-данные уже находятся в БД;
какие функции уже реализованы и пригодны для расширения.
0.2. Фиксация контрактов
Создаём проектные документы в репозитории, например:

text
docs/
  architecture.md
  game-rules.md
  admin-permissions.md
  economy-and-root-ledger.md
  mission-state-machines.md
  api-contracts.md
  security-and-audit.md
Это не «лишняя бюрократия»: документы будут эталоном, по которому мы проверяем, что новая фича не нарушает игровые правила.

Результат этапа
понятный список уже реализованного;
список технического долга;
утверждённые игровые правила;
последовательный план миграций;
никаких рискованных изменений в данных.
Этап 1. Фундамент: безопасность, роли, аудит, системные настройки
Цель: сначала построить безопасный административный контур. После этого создание миссий, платежи и ручные действия не будут «дырой» в системе.

1.1. Супер-админ и управление администраторами
Текущий owner преобразуем в модель супер-админа.

Супер-админ сможет:

создавать администраторов;
приглашать/активировать/деактивировать админов;
удалять админов;
назначать индивидуальные полномочия;
отзывать отдельные полномочия;
задавать режим исполнения каждого полномочия:
самостоятельное выполнение;
выполнение только после одобрения супер-админа;
просматривать действия, заявки и решения;
управлять системными настройками;
назначать дополнительных супер-админов.
Ограничения
нельзя удалить или отключить последнего активного супер-админа;
админ не может выдать себе право;
админ не может назначить права выше своих;
админ не может одобрить собственную заявку;
права на финансовые действия, блокировки, удаление данных и публикацию контента могут требовать одобрения;
все изменения прав логируются.

Для каждого разрешения супер-админ выбирает:

  direct

1.3. Заявки на подтверждение
Добавляется сущность AdminApprovalRequest.

Она хранит:

целевой объект: игрок, миссия, кошелёк, админ и т. п.;
снимок параметров операции;
причину;
статус;
дату создания и истечения;
одобрившего/отклонившего супер-админа;
комментарий решения;
фактический результат исполнения.
Статусы:

text

rejected
cancelled
expired
executed
execution_failed
1.4. Неизменяемый аудит
Улучшаем существующий admin_audit_log.

Каждая операция должна включать:

text
who:
  admin_id
  admin_username
  permission_used

what:
  action_type
  resource_type
  resource_id

before / after:
  безопасный снимок изменённых данных

  reason
  request_id
  ip_address
  user_agent
  approval_request_id, если применимо
  result
Пароли, ключи сессий, токены, хэши и секреты никогда не должны попадать в лог.

Результат этапа
Безопасная админская основа, на которой можно строить контент, экономику и модерацию.

Этап 2. Полноценная CMS игровых заданий
Цель: убрать конкретные миссии из кода и дать супер-админу/делегированным администраторам возможность создавать игру через админку.

2.1. Управление контентными сущностями
Админка получает полный CRUD для:

text
Сезоны
Главы
Сюжетные узлы
Миссии
Требования миссий
Награды миссий
Предметы
Ключи доступа
Пулы случайных наград
Геозоны
AR-объекты
Конфигурации мини-игр
Каждая сущность проходит жизненный цикл:

text
draft → published → archived
Физическое удаление по умолчанию не делаем: старые данные могут быть связаны с прогрессом игроков, наградами и финансовыми проводками.

2.2. Миссии трёх типов
Вводим универсальные значения:

text
solo
team
global
Базовое правило:

text
У игрока одновременно:
- не более 1 активной solo-миссии;
- не более 1 активной team-миссии;
- не более 1 активной global-миссии.
То есть одновременно допустимо:

text
1 personal + 1 team + 1 global
Лимиты хранятся в системных настройках админки, а не в коде. В перспективе можно добавлять исключения для сезонов или особых событий.

2.3. Требования доступа
Для каждой миссии через админку настраиваются:

завершение других миссий;
наличие предмета/ключа;
минимальный выигрыш ROOT;
минимальный уровень/статус игрока, если позже появится;
нахождение в команде;
размер команды;
страна/регион;
временное окно;
лимит повторного прохождения;
индивидуальные условия видимости.
Проверки должны предотвращать:

ссылку миссии на саму себя;
циклические зависимости вида A → B → C → A;
ссылку на архивный/несуществующий контент;
публикацию миссии с недействительными наградами.
2.4. Миграция demo-контента
Только когда CMS полностью готова:

- [x] отключаем python -m app.seed при обычном запуске backend (сделано: 3.11.b — guard APP_ENV=production, авто-вызовов нет);
- [x] demo seed переводим в отдельный ручной development-инструмент (сделано: 3.11.b — python -m app.seed, dev-only);
сохраняем резервную копию текущей БД;
удаляем/архивируем demo-сезон, главы, миссии, предметы и прогресс;
- [x] удаляем публичные demo API, включая reset-demo-progress (сделано: 3.11.a);
проверяем, что backend не создаёт задания при рестарте.
Результат этапа
Ни одно конкретное задание, название, награда, ключ или геозона не находится в исполняемом коде.

Этап 3. Инвентарь и ключи доступа
Цель: реализовать экономику ключей как управляемую контентную систему.

3.1. Ключи
Ключ — это предмет специального типа, но с дополнительными игровыми правилами.

Настраиваемые параметры ключа:

text
code
title
description
symbol / visual
rarity
status
is_consumable
stack_limit
sort_order
3.2. Взятие миссии
Для любой миссии администратор указывает:

text
entry_fee_root
required_key_item_id
required_key_quantity
При принятии миссии атомарно:

проверяется статус игрока;
проверяется тип миссии и лимит активных миссий;
проверяется наличие требуемого ключа;
проверяется ROOT-баланс;
ROOT списывается через ledger;
ключ безвозвратно списывается из инвентаря;
создаётся экземпляр миссии игрока/команды;
создаются activity events.
Ключ не возвращается:

при отмене;
при истечении времени;
после всех неудачных попыток;
при блокировке игрока;
при принудительном закрытии миссии, кроме отдельной ручной компенсации через админку.
3.3. Три попытки и награда
Для миссии настраиваются:

text
max_attempts: 3

attempt_reward_multipliers:
  attempt_1: 1.00
  attempt_2: 0.50
  attempt_3: 0.25
Игрок заранее видит:

стоимость входа;
необходимый ключ;
число попыток;
базовую награду ROOT;
награду за 1-ю, 2-ю и 3-ю успешную попытку;
тип ключевой награды;
является ли ключ гарантированным или случайным.
3.4. Персональный магазин после первой неудачи
Если игрок провалил первую попытку миссии, создаётся персональная разблокировка магазина.

Правило:

text
Игрок P провалил попытку №1 миссии M
→ ключи, являющиеся наградой миссии M,
  становятся доступны для покупки только игроку P.
Настройки на уровне награды/миссии:

text
shop_unlock_on_first_failure
shop_price_root
shop_purchase_limit_per_player
shop_available_for_seconds / no_expiry
shop_offer_mode:
  exact_key
  random_key_from_pool
По умолчанию предпочтителен режим:

text
exact_key
То есть игрок видит и покупает конкретный ключ за ROOT.

Нельзя:

продавать ключи;
передавать ключи другим игрокам;
обменивать ключи;
открывать магазин всем игрокам после провала одного человека.
Результат этапа
Полный цикл: миссия → награда ключом → провал первой попытки → персональная возможность купить ключ за ROOT.

Этап 4. Игроки, карточка игрока, ручные операции и ограничения
Цель: дать администрации полный операционный контроль без прямого доступа к БД.

4.1. Карточка игрока
В админке отображаются:

text

последняя активность

команда

активные миссии
история миссий и попыток

ограничения и блокировки
события, ошибки, обращения
заметки администрации
4.2. Ручные действия
Через админку, с причиной и аудитом:

начислить ROOT;
списать ROOT;
выдать ключ/предмет;
отозвать ключ/предмет;
добавить игрока в команду или исключить;
снять игрока с миссии;
отменить миссию;
принудительно завершить миссию;
вручную начислить награду;
скорректировать попытки только через контролируемую операцию;
восстановить/заблокировать доступ;
завершить активные пользовательские сессии;
экспортировать историю игрока.
Чувствительные операции могут требовать подтверждения супер-админа.

4.3. Статусы и ограничения игрока
Статус игрока не должен быть только is_active.

Пример:

text

У ограничения есть:

text

Результат этапа
Поддержка игроков осуществляется через админку, а не SQL-командами или ручными правками БД.

Этап 5. Команды, приглашения, состав и чат
Цель: создать безопасную командную систему.

5.1. Команда и участники
Сущности:

text
Team
TeamMember
TeamInvitation
TeamJoinRequest
TeamMembershipHistory
Возможности:

создать команду;
назначить название, описание, эмблему;
открыть/закрыть набор;
настроить вступление:
открытое;
по заявке;
только по приглашению;
пригласить игрока;
принять или отклонить заявку;
выйти из команды;
исключить участника;
передать лидерство;
расформировать команду;
видеть историю состава.
Базовое правило:

text
Игрок состоит максимум в одной активной команде.
5.2. Командный чат
Чат существует, пока существует команда.

Поддерживаем:

обычные сообщения;
системные события;
удаление/скрытие сообщений модератором;
жалобы;
мут участника;
заморозка чата;
просмотр истории супер-админом;
журнал модерации.
Когда команда расформирована:

отправка сообщений прекращается;
игрокам история скрывается;
записи сохраняются для аудита и расследований.
5.3. Правила выхода при активной командной миссии
Нужно реализовать настраиваемую системную policy. Базовый безопасный вариант:

text
Игрок не может выйти из команды,
если участвует в активной командной миссии.
Исключение — ручное действие администратора с причиной и возможным approval.

Результат этапа
Команды, состав, приглашения и чат управляются через админку и имеют полноценную историю.

Этап 6. Командные задания и совместная геоактивация
Цель: реализовать модель: вся команда в зоне → объект появляется → каждый проходит индивидуально.

6.1. Два уровня командной миссии
Уровень 1: активация команды
Все требуемые участники должны находиться в игровой зоне.

Настройки миссии:

text
min_participants
max_participants
required_participants_count
require_all_mission_participants_present
presence_window_seconds
minimum_presence_duration_seconds
max_location_accuracy_meters
После успешного подтверждения присутствия:

text
team mission run → activated
AR-объект становится доступным.

Уровень 2: индивидуальное завершение
После активации каждый участник:

выполняет мини-игру отдельно;
имеет свои три попытки;
получает личный результат;
получает полную награду согласно номеру своей успешной попытки;
может провалить миссию независимо от других.
Пример при базовой награде 100 ROOT:

Игрок	Успешная попытка	Награда
A	1	100 ROOT
B	2	50 ROOT
C	3	25 ROOT
Награда не делится. Каждый получает её полностью по своему результату.

6.2. Вход в командную миссию
Базовое правило, которое следует реализовать как настройку миссии:

text
Каждый участник платит собственный entry fee в ROOT
и расходует собственный входной ключ.
Это соответствует индивидуальным наградам и предотвращает ситуацию, когда лидер финансирует всех без явной настройки.

В будущем можно добавить режимы:

text
individual_payment
leader_pays_for_all
split_cost_equally
team_treasury_payment
Но в первой версии нужен только individual_payment.

Результат этапа
Командная геомиссия не сводится к одной кнопке: присутствие коллективное, прохождение и награды — индивидуальные.

Этап 7. Геолокация, карта, AR-объекты и античит
Цель: создать технически реалистичную основу для игрового сценария наподобие Pokémon Go.

7.1. Геозоны
Админка позволяет создавать:

text
radius zone
polygon zone
point of interest
time-limited event zone
Параметры:

text
latitude / longitude
radius_meters
polygon_coordinates
timezone
starts_at / ends_at
schedule
max_location_accuracy_meters
minimum_presence_seconds
cooldown rules
7.2. AR-объект
Через CMS настраиваются:

тип объекта;
3D/2D-ассет или ссылка на ассет;
место/правило появления;
время доступности;
сценарий обнаружения;
мини-игра;
инструкция игроку;
конфигурация валидации;
награды.
7.3. Защита от подмены геолокации
Минимальный набор:

фиксировать точность координат;
проверять время и частоту обновления;
определять невозможную скорость перемещения;
не принимать устаревшие координаты;
требовать присутствие в зоне заданное время;
фиксировать устройство и сессию;
добавлять антифрод-флаги;
отправлять подозрительные события в админку.
Нельзя полагаться только на GPS: подмену геолокации полностью устранить невозможно, поэтому нужна комбинация проверок и ручной модерации.

7.4. Персональные данные
Геолокация — чувствительные данные. Потребуются:

согласие игрока;
понятная политика использования;
минимизация хранимых координат;
сроки хранения;
удаление или обезличивание по политике;
доступ к истории геоданных только у ограниченного круга админов.
Результат этапа
Геозоны и AR-сценарии настраиваются через админку, а не создаются в коде.

Этап 8. Экономика ROOT и финансовый ledger

Этап 9. Переводы ROOT между игроками и комиссия в Telegram Stars
Цель: ввести внутренние переводы по вашему правилу.

9.1. Условие доступа к переводам
Игрок может отправлять ROOT другому игроку, только если его суммарный подтверждённый выигрыш достиг порога.

По умолчанию:

text
minimum_earned_root_for_transfer = 50 ROOT
Но значение редактируется супер-админом через настройки.

Важно: считаем именно подтверждённый выигрыш из разрешённых источников, а не текущий баланс. Игрок не должен разблокировать переводы, просто получив ROOT от другого игрока.

9.2. Комиссия Stars
Бизнес-правило:

text
внутренний перевод ROOT возможен после достижения порога выигрыша;
комиссия за перевод уплачивается в Telegram Stars.
Перед реализацией обязательно отдельно проверяем текущие возможности Telegram Stars API и правила Telegram для вашего конкретного сценария. Комиссия должна оплачиваться в официальный адрес/бот проекта, а не переводиться напрямую между пользователями.

Технический процесс должен быть таким:

игрок создаёт намерение перевести ROOT;
сервер рассчитывает сумму ROOT и комиссию Stars;
игрок оплачивает Stars-инвойс;
Telegram подтверждает платёж;
сервер атомарно проводит перевод ROOT;
создаются две ROOT-проводки: debit отправителя и credit получателя;
создаётся запись комиссии и платежа Stars;
при ошибке перевод не выполняется или корректно компенсируется.

Этап 10. Вывод ROOT в TON-кошелёк
Цель: реализовать безопасный вывод игрового ROOT на внешний TON-кошелёк.

> **СДЕЛАНО И РАБОТАЕТ (testnet, первая реальная выплата прошла 25.11.2026).**
>
> Схема: сервер формирует батч заявок с уникальными `query_id` → владелец
> подписывает переводы в Tonkeeper через TON Connect → сервер сверяет БЛОКЧЕЙН
> и подтверждает каждую заявку отдельно. Приватный ключ на сервере отсутствует.
>
> Фактическая реализация:
> - `payout_batch_service.py` — сборка батча, один открытый батч через
>   частичный UNIQUE-индекс (защита от трёх воркеров gunicorn);
> - `ton_connect_parser.py` — разбор BOC, проверка подписи Ed25519, V4 и V5R1;
> - `payout_confirm_service.py` — сверка подписи, отправителя, `query_id`,
>   точной суммы и адреса владельца;
> - `ton_payout_lookup.py` — проверка ДОСТАВКИ (входящий `internal_transfer`
>   на jetton-кошелёк получателя), а не только факта отправки;
> - `payout_rollback_service.py` — откат с возвратом в `pending`, защита
>   подтверждённых заявок, автооткат по таймауту (CMS
>   `ton.payout_processing_timeout_hours`);
> - старый путь автоотправки с мнемоникой на сервере ВЫКЛЮЧЕН: `POST
>   /admin/withdrawals/batch` отдаёт 410 без CMS-тумблера
>   `ton.legacy_autopayout_enabled`.
>
> Фактические статусы заявки: `pending → processing → confirmed | failed`.
> Целевая модель ниже (draft/submitted/under_review/reserved/broadcasting)
> НЕ реализована и не нужна при внешней оплате.
>
> Подробности — `withdrawal-external-payout.md` и
> `withdrawal-external-payout-plan.md`.
>
> **Что осталось по этапу:** автоматическое подтверждение без кнопки
> (сейчас админ нажимает «Сверить»), поддержка API-ключа TonCenter (сейчас
> анонимный лимит ~1 запрос/сек).

Открытый технический долг (приоритет сверху вниз)
1. **PostgreSQL-тесты гонок не выполняются.** `tests/test_economy_pg_9_3_1.py`
   (конкурентные покупки, идемпотентность fallback) пропускается без локального
   PostgreSQL. SQLite не моделирует `FOR UPDATE` — это единственная
   непроверенная область в деньгах.
2. **Deposit poller работает от `root`** (`deploy/root-game-deposit-poller.service`),
   хотя основной сервис — от `deployer`. В юните стоит TODO.
3. **`deposit_service.process_incoming_transfer` не сверяет `to_address`** с
   активным `ton.deposit_wallet`. Сейчас безопасно (poller запрашивает только
   свой адрес), но проверка должна быть в самом сервисе.
4. **Нет security headers в nginx** (HSTS, CSP, X-Frame-Options,
   X-Content-Type-Options) — см. аудит, находка F-02.
5. **Античит не отменяет награду.** Телепорт → миссии выполнены → ROOT начислены
   → флаг → заблокирован только вывод. Требует решения владельца: блокировать
   награду сразу или оставлять до разбора админом.
6. **`/health` раскрывает `environment`** — мелочь, но лишнее.
7. **TonCenter без API-ключа** — анонимный лимит ~1 запрос/сек, для батча из 50
   заявок мало.
8. **Автоподтверждение выплат** — сейчас кнопка «Сверить» вручную.
9. **Регулярные бэкапы и восстановление БД** — в roadmap заявлены, в репозитории
   нет автоматизации.
10. **Уязвимые dev-зависимости frontend** по `pnpm audit` (Vite/source-map-js);
    влияют только на dev/CI, но обновить надо.

Что НЕ начинать без отдельного решения
- Переписывать статусную модель заявок на целевую (draft/submitted/…): при
  внешней оплате она не нужна, а миграция затронет деньги.
- Возвращать автоотправку с мнемоникой на сервере: это ровно тот риск, ради
  устранения которого сделаны внешние выплаты.
