# Выплаты ROOT в TON — ручная оплата из кошелька владельца

Документ описывает **действующий** механизм вывода ROOT в TON: сервер готовит
батч, владелец игры подписывает переводы в Tonkeeper, сервер сверяет блокчейн.

Приватный ключ кошелька выплат **никогда не попадает на сервер**. Сервер не
может отправить деньги сам — он умеет только проверить, что деньги ушли.

План внедрения (по шагам, с историей решений) — `withdrawal-external-payout-plan.md`.

## 1. Зачем так

Прежняя схема хранила мнемонику кошелька в `.env` на сервере
(`TON_PAYOUT_MNEMONIC`) и отправляла переводы автоматически. Это означало:
утечка сервера = утечка кошелька.

Текущая схема: сервер выдаёт список заявок с уникальными `query_id`, владелец
подписывает пачку на своём устройстве, сервер находит каждый перевод в
блокчейне и закрывает заявки. Компромисс сервера больше не даёт доступа к
деньгам.

Старый путь `send_jetton_transfer` (автоотправка с мнемоникой из `.env`)
**заблокирован**: эндпоинт `POST /api/v1/admin/withdrawals/batch` отдаёт 410,
кнопка убрана из админки. Код сохранён как аварийный и включается только
осознанно — CMS-ключ `ton.legacy_autopayout_enabled = true`.

Включать его стоит лишь если внешние выплаты недоступны (например, TON API
лежит, а деньги выдать надо срочно). Помните: он требует `TON_PAYOUT_MNEMONIC`
на сервере, то есть возвращает тот самый риск утечки ключа, ради устранения
которого делались внешние выплаты.

## 2. Жизненный цикл

### 2.1. Заявка игрока

```
pending ──(батч)──> processing ──(confirm)──> confirmed
                          └──(rollback)──> pending  (холд сохранён)
                                      └──> failed   (холд возвращён)
```

| Статус | Что значит | ROOT игрока |
|---|---|---|
| `pending` | ждёт батча | списан в холд |
| `processing` | вошла в батч, ждёт оплаты | в холде |
| `confirmed` | перевод найден в блокчейне | ушёл игроку |
| `failed` | выплата не состоится | возвращён на баланс |
| `rejected` | отклонена админом | возвращён на баланс |

### 2.2. Батч

```
ready ──(confirm, всё оплачено)──> confirmed
   │
   ├──(confirm, часть оплачена)──> submitted
   └──(rollback)────────────────> rolled_back
```

| Статус | Что значит |
|---|---|
| `ready` | сформирован, ждёт оплаты |
| `submitted` | оплачен частично, часть заявок ещё не видна в блокчейне |
| `confirmed` | все заявки подтверждены |
| `rolled_back` | снят, заявки возвращены или провалены |

**Один открытый батч на систему.** Держит частичный unique-индекс в БД, а не
логика приложения: планировщик живёт в каждом из трёх воркеров gunicorn, и без
барьера создавались бы три батча одновременно.

## 3. Как выплатить (пошагово)

1. Админка → вкладка **«Батчи выплат»** → «Сформировать батч».
   Все `pending` (кроме игроков с ограничением на вывод) переходят в
   `processing`, каждая получает `query_id`.
2. Раскрой батч, проверь список: суммы, адреса, `jetton wallet`.
   Если `jetton wallet` = «не определён» — оплата заблокирована, см. §7.
3. «Подключить кошелёк» → Tonkeeper → подтверди подключение.
   Кошелёк должен совпадать с `ton.payout_wallet`, иначе сервер отклонит BOC.
4. «Оплатить батч» → в Tonkeeper проверь список переводов → подтверди.
5. Сервер получит подписанный BOC и проверит:
   подпись, отправителя, соответствие переводов заявкам, наличие каждого
   перевода в блокчейне.
6. Результат появится в панели: «подтверждено N из M» и перечень ненайденных.

Пункт 6 — самое важное место. Транзакция в TON может выполниться **частично**:
часть переводов проходит, часть отклоняется (bounce). Поэтому подтверждение
идёт по каждой заявке, а не «батч прошёл целиком».

## 4. Что делать при частичной оплате

Батч останется в `submitted`, неоплаченные заявки — в `processing`.

**Если переводы ещё не долетели** — подожди и повтори подтверждение тем же
BOC через `POST /api/v1/admin/withdrawals/payout-batches/{id}/confirm`
(в UI отдельной кнопки повтора нет; батч в статусе `submitted` принимает
повторный confirm). Фоновый джоб откатит батч по таймауту, если ничего не
делать.

**Если часть переводов отклонена блокчейном** — откати остаток:
«Откатить» → «2 — отклонить и вернуть ROOT игрокам». Оплаченные заявки не
тронутся, они в `confirmed`.

## 5. Откат

Два режима, выбираются при откате:

| Режим | Заявки | ROOT |
|---|---|---|
| `return_to_pending` | снова `pending`, ждут нового батча | остаётся в холде |
| `fail_and_refund` | `failed` | возвращается на баланс с проводкой `credit` |

Когда что:

- **ошибся батчем, не тот кошелёк, передумал** → `return_to_pending`;
- **выплата не состоится вообще** → `fail_and_refund`.

`confirmed`-заявки **не откатываются никогда**, даже с `force=true`: деньги уже
ушли в блокчейн, «вернуть» их в базе означало бы записать двойную трату.
Для частично подтверждённого батча нужен `force=true` — он откатит только
неоплаченный остаток.

### Авто-откат по таймауту

Батч, висящий дольше `ton.payout_processing_timeout_hours` (по умолчанию 24 ч),
откатывается в `pending` фоновым джобом (планировщик `retention.py`, ежечасно
в :15). Возврат денег автоматика не делает — это осознанное решение админа.

## 6. Что настроить

### 6.1. CMS (админка → Настройки)

| Ключ | Значение | Зачем |
|---|---|---|
| `ton.withdrawal_enabled` | `true` | глобальный рубильник вывода |
| `ton.payout_wallet` | адрес | с какого кошелька платим |
| `ton.payout_wallet_public_key` | hex, 32 байта | проверка подписи BOC |
| `ton.payout_processing_timeout_hours` | 24 | авто-откат зависших батчей |
| `ton.min_amount_root` | 10 | минимальная заявка |
| `ton.daily_withdrawal_limit` | 5000 | дневной лимит на игрока |
| `ton.legacy_autopayout_enabled` | `false` | старая автовыплата с мнемоникой; только для аварии |

Без `ton.payout_wallet_public_key` подтверждение честно отказывает с 503:
нечем проверить подпись.

**Где взять публичный ключ.** Это не секрет: по нему можно только проверить
подпись, подделать её нельзя. Формат — 64 hex-символа (32 байта).

Надёжный способ — вывести из сид-фразы кошелька офлайн, не вводя её на сервере
(код проверен: даёт ту же пару ключей, которой подписывает кошелёк):

```python
# локально, в отдельном окружении; сид-фраза вводится с клавиатуры
from pytoniq_core.crypto.keys import mnemonic_to_wallet_key

mnemonic = input("Сид-фраза кошелька выплат: ").split()
public_key, _private_key = mnemonic_to_wallet_key(mnemonic)
print(public_key.hex())   # 64 hex-символа — это и есть значение для CMS
```

Если в вашем кошельке (Tonkeeper, MyTonWallet) есть пункт экспорта публичного
ключа — можно взять оттуда, но наличие такого пункта зависит от версии
приложения. Сид-фраза на сервер не попадает никогда.

### 6.2. Переменные окружения (`.env`, backend)

| Переменная | Зачем |
|---|---|
| `TON_API_ENDPOINT` | TonCenter с ключом: сверка блокчейна и адреса jetton-кошельков |
| `TON_ROOT_JETTON_MASTER` | адрес jetton-мастера ROOT |
| `TON_NETWORK` | `testnet` или `mainnet` |

Без `TON_API_ENDPOINT` кнопка оплаты блокируется: сервер не может вычислить
jetton-кошелёк получателя, а переводить на обычный адрес нельзя — деньги
потеряются.

## 7. Диагностика

| Симптом | Причина | Что делать |
|---|---|---|
| «Оплата невозможна» у заявок | не настроен `TON_API_ENDPOINT` или `TON_ROOT_JETTON_MASTER` | проверить `.env`, перезапустить бэкенд |
| 422 «Подпись BOC не подтверждена» | не тот `payout_wallet_public_key` или кошелёк не тот | сверить ключ с кошельком |
| 403 «BOC подписан другим кошельком» | платили не с `ton.payout_wallet` | подключить правильный кошелёк |
| 422 «Сумма по заявке не совпадает» | подписан BOC от другого батча | сформировать батч заново и оплатить текущий |
| 409 «Батч уже подтверждён» | повторное подтверждение | ничего не делать, это защита от дубля |
| 409 «Батч подтверждён: откат невозможен» | пытались откатить закрытый батч | откатывать нечего |
| «Подтверждено 0 из N» | переводы ещё не в блокчейне | подождать, сверка повторяема |
| Неоплата висит днями | забыли батч | авто-откат сработает по таймауту |
| 410 на `/withdrawals/batch` | старый путь выключен намеренно | использовать «Батчи выплат» |

## 7a. Версии кошельков

Поддерживаются два формата внешнего сообщения, и они **несовместимы**:

| | V4 (WalletV4R2) | V5R1 (Tonkeeper сейчас) |
|---|---|---|
| первые 32 бита | начало подписи | `0x7369676e` ("sign") |
| подпись | в начале ячейки | последние 512 бит |
| список сообщений | цепочка ref'ов | дерево `prev + action` в обёртке `packed` |

Версия определяется автоматически по первым 32 битам. Если парсер ждёт V4, а
кошелёк V5 — он прочитает op-код как `wallet_id` и не найдёт переводы.
Симптом в админке: «Подпись BOC не подтверждена» или «В BOC нет ни одного
jetton-перевода».

Проверить версию своего кошелька: в Tonkeeper → адрес → подробности
(«W5» в названии = V5), либо по data-ячейке (первый бит `is_signature_allowed`
у V5).

## 8. Инварианты (не нарушать)

1. `confirmed`-заявка не откатывается. Деньги в блокчейне.
2. Перевод идёт на `jetton wallet` игрока, не на его обычный адрес.
3. Подпись BOC проверяется ed25519; отправитель сверяется с `ton.payout_wallet`.
4. Сумма и получатель каждого перевода сверяются с заявкой по `query_id`.
5. Подтверждение — по каждой заявке, никогда по хешу батча.
6. Один открытый батч на систему (барьер в БД).
7. Физическое удаление заявок и батчей запрещено: история выплат append-only.

## 11. Что НЕ входит

- Мультиподпись (несколько админов на одну выплату).
- Автоматическая выплата без человека.
- Хранение приватного ключа на сервере.
- Удаление `send_jetton_transfer` — остаётся аварийным путём, выключенным по
  умолчанию (CMS `ton.legacy_autopayout_enabled`).
