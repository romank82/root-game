# Вывод ROOT → TON через внешний кошелёк (Tonkeeper) — план

Статус: **план, требует согласования**. Дата: 2026-11-23.
Заменяет: хранение `TON_PAYOUT_MNEMONIC` на сервере для выплат.

## 1. Цель

Убрать приватный ключ выплатного кошелька с сервера и при этом сохранить
корректный учёт ROOT: игрок не должен получить деньги дважды, а баланс в
базе не должен разъезжаться с блокчейном.

Итог: сервер **не платит**, а готовит данные. Платит владелец игры из
Tonkeeper на своём телефоне. Сервер сверяет факт оплаты с блокчейном и только
потом закрывает заявки.

**Ключевой факт учёта:** ROOT списывается в холд при создании заявки, а не при
выплате. Значит «не изменился баланс после выплаты» — это норма: он изменён
заранее, при подаче. Двойного вывода не будет, потому что деньги уже не на
балансе.

## 3. Что пишем с нуля

### 3.1. Модель `PayoutBatch` (новая таблица)

Сейчас батч — это только `batch_id` (строка) в заявке и в `PayoutAttempt`.
Для ручной схемы нужен объект с состоянием, потому что между экспортом и
подтверждением проходит время.

Поля:
- `id` (`batch-...`, PK)
- `admin_id` — кто экспортировал/сформировал
- `status` — `ready | submitted | confirmed | rolled_back`
- `total_nano` — сумма батча на момент формирования
- `payload_text` — готовый текст для Multisend (для истории и повтора)
- `tx_hash` — хеш из блокчейна (после подтверждения)
- `opened_at` — когда открыт (для контроля «висит N дней»)
- `created_at`, `updated_at`, `terminal_at`

Зачем: без отдельного объекта невозможно ответить «что было в этом батче» и
«почему заявка в processing двое суток».

**Решения заказчика (2026-11-23):**

1. **Батч = все `pending` на момент формирования**, без привязки к
   календарным суткам. Заявка, поданная в 23:58, попадает в ближайший батч —
   игрок ждёт максимум сутки. Границы периода восстанавливаются по датам
   самих заявок (min–max), для отчётности ничего не теряется.
2. **Один открытый батч.** Пока есть батч в `ready`/`submitted`, новый не
   создаётся — новые заявки добавляются в открытый. Поэтому в списке не может
   быть пяти «на оплату», и один хеш всегда соответствует одному батчу.

**Защита от трёх воркеров gunicorn.** Планировщик APScheduler живёт в
`lifespan`, то есть в каждом из 3 воркеров. Защита `if _scheduler is not None`
работает внутри процесса и не спасает. Решение — **частичный unique-индекс в
БД**:

```sql
CREATE UNIQUE INDEX uq_payout_batches_one_open
    ON payout_batches ((1))
    WHERE status IN ('ready', 'submitted');
```

Второй и третий воркер упрутся в ограничение и создадут ноль батчей вместо
двух лишних. Это защита на уровне данных, а не логики.

**Ежедневная проверка.** Джоб в 01:00 UTC (форa час, чтобы заявки 23:59
успели зафиксироваться): если открытого батча нет — создать из накопленных
`pending`. Плюс кнопка «Сформировать» для ручного запуска после сбоя.

### 3.2. Статус `processing` уже есть — добавляем переходы

Модель `WithdrawalRequest` не имеет `CheckConstraint` на `status`, миграция
не нужна. Переходы:

```
pending --export--> processing --confirm--> confirmed
                          \--rollback--> pending | failed(+refund)
```

### 3.3. Сервис сверки через TON API (`ton_service.py`)

Новый метод `_TonCenterProvider.find_jetton_transfer_by_hash(...)`:

1. `getTransactions` по адресу плательщика (`ton.payout_wallet`) — постранично
   по курсору `lt/hash`, пока не найдётся нужный хеш или кончится глубина.
2. Для каждой tx: `parse_jetton_transfer`-подобный разбор **исходящего**
   сообщения (OP `0xf8a7ea5`, `internal_transfer` не подходит — это входящий).
   Извлекаем: destination owner, amount nano, `query_id`.
3. Возвращает `{found: bool, tx_hash, items: [{address, amount_nano, query_id}]}`.

**Важно:** исходящий jetton-перевод виден в блокчейне как сообщение
**от jetton-wallet плательщика**, а не от его основного кошелька. Поэтому
искать нужно по адресу jetton-wallet, который вычисляется через
`get_jetton_wallet_address(minter, payout_address, provider)` — функция уже
есть.

### 3.4. `query_id` как ключ сверки

`PayoutAttempt.query_id` уже существует (uint64). Предлагаю новую схему:

- При экспорте каждой заявке создаётся `PayoutAttempt(status='sending')`
  с `query_id = случайный uint64`.
- Текст для Multisend формируется с этими `query_id` — если формат позволяет.
- При подтверждении сервер сверяет по `query_id`, а не по адресу+сумме.
  Это устойчиво к совпадениям сумм.

**Открытый вопрос:** поддерживает ли Tonkeeper Multisend `query_id`.
Если нет — сверяем по адресу+сумме, а `query_id` остаётся для идемпотентности
на уровне нашей БД. Решение примем после проверки документации TON.

### 3.5. Эндпоинты (admin, permission `players.manage`)

| Метод | Путь | Что делает |
|---|---|---|
| `POST` | `/admin/withdrawals/export` | pending → processing, создаёт `PayoutBatch`, возвращает `payloadText` + список заявок |
| `POST` | `/admin/withdrawals/confirm` | принимает `batchId` + `txHash`; сверяет через TON API; при совпадении — `confirmed` всем заявкам батча |
| `POST` | `/admin/withdrawals/rollback` | `processing` → `pending` (или `failed` + возврат холда) по решению админа |
| `GET` | `/admin/withdrawals/batches` | история батчей (для разбора спорных случаев) |

Все — в `admin_withdrawals.py`, аудит через `write_admin_audit`
(`withdrawal.exported`, `withdrawal.confirmed`, `withdrawal.rolled_back`).

### 3.6. Таймаут `processing`

Настройка CMS: `ton.payout_processing_timeout_hours` (default 24).
Фоновый джоб (паттерн `retention.py`) возвращает просроченные заявки в
`pending` и пишет предупреждение в лог. Без этого забытый батч держит деньги
игрока вечно.

### 3.7. Фронтенд (`WithdrawalsSection.tsx`)

- Кнопка **«Экспорт для Tonkeeper»** вместо/рядом с «Выплатить батч».
- Модалка: текст для копирования, список заявок, сумма.
- Поле **«Хеш транзакции»** + кнопка **«Подтвердить»**.
- Результат сверки: «найдено: N переводов, суммы совпадают» или конкретное
  расхождение («перевод на 50 ROOT не найден»).
- Кнопка **«Откатить батч»** с подтверждением.

## 4. Как будет проходить списание ROOT (главный вопрос заказчика)

### Сценарий успеха

| Шаг | Что делает | Баланс игрока | Статус заявки |
|---|---|---|---|
| 1 | Игрок подаёт заявку на 100 | **100 → 0** (холд) | `pending` |
| 2 | Админ жмёт «Экспорт» | 0 (не меняется) | `processing` |
| 3 | Админ платит в Tonkeeper | 0 (не меняется) | `processing` |
| 4 | Админ вводит хеш, сервер сверяет | 0 (не меняется) | `confirmed` |
| — | ROOT в игре у игрока нет, 100 ROOT ушли в блокчейн | 0 | — |

**Итог: баланс и блокчейн согласованы.** Игрок отдал 100 ROOT в игре и получил
100 ROOT-jetton на TON-адрес.

### Сценарий провала

| Шаг | Что делает | Баланс | Статус |
|---|---|---|---|
| 1 | Заявка подана | 100 → 0 | `pending` |
| 2 | Экспорт | 0 | `processing` |
| 3 | Админ не заплатил / ошибся | 0 | `processing` |
| 4 | Откат батча | **0 → 100** (возврат) | `failed` |

Проводка возврата — существующая `_refund_withdrawal_hold`, новой логики не
требуется.

### Почему двойной выплаты не будет

1. Холд списывается **до** выплаты — повторно вывести те же ROOT физически
   нельзя (`wallet.available_balance` уже уменьшен).
2. Экспорт переводит в `processing` — повторный экспорт эти заявки не увидит.
3. `PayoutAttempt` unique-индекс по `(withdrawal_id) WHERE status IN
   ('sending','sent')` не даст создать вторую попытку.
4. Подтверждение идёт **только** по хешу, найденному в блокчейне. Нет
   транзакции — нет `confirmed`.

### Что защищает от подделки подтверждения

- Сверка не по введённому тексту, а по данным TON API.
- Проверяется: jetton-мастер = ROOT, получатели = адреса из заявок, суммы
  совпадают, отправитель = наш payout-кошелёк.
- Хеш уникален: `WithdrawalRequest.ton_tx_hash` не даст привязать одну
  транзакцию к двум заявкам (нужен unique-индекс — добавить в миграции).

## 8. Порядок работ (по шагам, каждый — отдельный коммит)

3. **Экспорт** (`POST /export`): pending → processing + батч. Тесты.
4. **Подтверждение** (`POST /confirm`): сверка + confirmed. Тесты.
5. **Откат** (`POST /rollback` + таймаут). Тесты.
6. **Фронтенд**: кнопки, модалка, поле хеша, результат сверки.
7. **Документ** `docs/withdrawal-external-payout.md` + обновление

## 9. Риски и как закрываем

| Риск | Вероятность | Закрытие |
|---|---|---|
| Tonkeeper Multisend не поддерживает `query_id` | средняя | сверка по адрес+сумма, `query_id` только для БД |
| Оплатили, но забыли подтвердить | высокая | таймаут `processing` + авто-откат, лог-предупреждение |
| Подтвердили не ту транзакцию | средняя | сверка через API, ручной ввод без проверки запрещён |
| Админ платит частями | средняя | разрешить несколько подтверждений на батч (по одной заявке) |
| TON API недоступен в момент подтверждения | средняя | 503 без изменения статусов, повтор возможен |

## 10. Что нужно от заказчика перед началом

1. **Кошелёк для выплат** — адрес, с которого будешь платить из Tonkeeper.
   Вписывается в CMS `ton.payout_wallet` (уже есть).
2. **`TON_API_ENDPOINT`** — адрес TON API с ключом (без него сверка не
   работает). Для testnet — toncenter testnet.
3. **`TON_ROOT_JETTON_MASTER`** — адрес jetton-мастера ROOT.
4. **Решение по `query_id`**: разрешаем сверку по адрес+сумма, или требуем
   поддержку `query_id` в Tonkeeper (тогда сначала проверяем вручную).
5. **Ответ на вопрос**: выплачиваем **весь батч за один раз** или
   допускаем частичную оплату с покомпонентным подтверждением?

## 11. Что НЕ входит в этот план

- Мультиподпись (несколько админов на одну выплату).
- Замена `TON_PAYOUT_MNEMONIC` на зашифрованное хранилище в БД.
- Автоматическая выплата без человека.
- Депозит ROOT (отдельный блокер, п.1 «Открытых долгов»).
